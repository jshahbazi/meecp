# Sol immutable CPU RoPE candidate

Implemented on 2026-10-11 as an unmeasured, default-disabled additive experiment. The [patch](../experiments/uzu-rust/patches/uzu-sol-rope.patch) applies to the accepted `runtime/uzu-rust/deep-optimization/all/source/upstream` snapshot, which includes the earlier scoring and deeper optimization patches. The separate working copy is `runtime/uzu-rust/sol-optimization/rope/source/upstream`. Historical sources, patches, builders, binaries and acceptance records remain unchanged.

Enable the new `uzu-engine/sol-rope-cache` feature to use model-owned CPU tables. Each deduplicated complete immutable RoPE configuration gets its own cache. Rows represent absolute positions, and the transformer retains its existing `context_length + topology.height` calculation. No tokens, sequence identity, hidden state, decisions or GPU buffers enter the cache. Model destruction drops the tables.

The cache lazily grows a dense prefix, bounded by the minimum of the configured maximum sequence length, 8192 positions and `1_048_576 / head_dim` positions. Retained cosine and sine vectors together occupy at most 8 MiB per distinct configuration. Growth temporarily holds the old vectors, new rows and replacement vectors; that transient allocation exceeds the retained bound. Positions outside the cap use the original CPU formula without being retained. Noncontiguous and duplicate positions preserve caller order through row gathering. Contiguous cached chunks allocate and upload GPU constants directly from the cached slices, avoiding two temporary output vectors. A mutex protects model-owned tables during growth and upload preparation.

## Exactness argument

The original CPU calculation is extracted mechanically into `precalculate_cpu_tables`: every inverse-frequency formula, scaling operation, f32/f64 cast, sine/cosine call and duplicated-half layout is retained. Both uncached computation and cache population call this helper. Stored rows are copied as f32 values without recomputation, reassociation or conversion. The complete configuration is cloned into each model-owned cache, so different bases, scaling parameters, factors, dimensions and sequence-length policies cannot share a table accidentally. Constant allocation order remains cosine then sine; GPU kernels, tensor dimensions, batch policy, attention geometry and full-vocabulary readout remain unchanged.

Source reasoning does not establish executable bit equality or a speed gain. The owning combined experiment subsequently passed compiled CPU/Metal tests and whole-vocabulary acceptance, as recorded below.

## Verification and limits

Two focused native tests are included. They compare f32 bits against fresh formula calculation for all five configuration families, both YARN truncation settings and both LongRoPE factor policies. They cover empty input, growth and reuse around 1024, nonzero chunk offsets, reordered/duplicate positions, cap boundaries, positions above exact integer-to-f32 range, maximum u32 position, distinct configurations and retained allocation bounds. These tests target indexing, reuse and fallback behavior; their shared formula helper does not independently validate the extracted arithmetic.

The implementation workstream performed source checks only. The owning experiment subsequently built the combined candidate and worker/probe, passed all 12 focused CPU/Metal tests, and completed exact native acceptance on 486 case outputs, 48 boundaries and 534 whole-vocabulary digests. Candidate logits, log probabilities, calibrated probabilities and typed decisions matched the sealed original Uzu reference bit-for-bit, including changed/repeated/restored requests and batch boundaries. Uzu retained fresh-state scoring and `cache_hit:false`; mathematical table reuse is independent of sequence reuse. See the [combined experiment](UZU_SOL_OPTIMIZATION.md) and its independent audit. Individual RoPE latency remains unmeasured.

The first use pays cache population and prefix-copy cost, and sparse high-position access can compute unused prefix rows. GPU constant allocation/upload remains per chunk. Mutex and scan overhead can exceed the removed work for tiny requests; configurations with many unique RoPE policies add separate bounded tables. Benchmark startup and request timing separately, and measure an additive candidate against the accepted worker before assigning any gain. This candidate does not modify DeltaNet/GDN, attention KV pruning, floating-point precision, calibration or production package integration.

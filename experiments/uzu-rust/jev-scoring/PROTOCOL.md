# JevK5 probability-scoring comparison

This protocol is fixed before inspecting engine scoring outputs. It evaluates the existing JevK5 v0.3 4B GGUF against Rust Uzu exports of the same merged checkpoint. Independently converted or quantized artifacts can differ numerically; token parity does not establish weight parity. No production engine or installed add-on is changed by this isolated experiment.

## Inputs and semantics

Use all 231 MIT-licensed public JevBench v1.2 items: easy 48, original 72, hard 111. Pin the upstream repository, source bytes, ordered cases, and rendered prompts in `DATASET_PROVENANCE.json`. Add authored known-answer synthetic cases covering yes/no, choice, score, Unicode/structured evidence, option order, and the 16-option boundary. Report these checks separately from public quality. Do not filter cases based on answers. Reject invalid criteria, missing candidate coverage, nonfinite logits/probabilities, token mismatches, over-context inputs, and truncation.

Use the vendored official prompt and decision mapping at `f944fe37ff1d5ed3830aa4c8d88b7189c8c1268a`. These files match the current upstream files at `f26426d16f59e8bbe1470e5b162cc89329e29b29`. Preserve letter temperature **1.22**, knockout temperature **0.93**, option order, special-token parsing, and the closed thinking prefix. With 2–16 options the knockout temperature is deliberately inactive, exactly as upstream. Tests cover its behavior for more options; runtime many-pass scoring is outside this experiment.

At the final prompt position, independently compute each declared option probability as `exp((logit - max_logit) / 1.22) / sum(...)`. Full-vocabulary log probabilities can replace logits because their common normalizer cancels. Require Uzu's returned candidate probabilities to match this independent formula within **1e-12 absolute error**. Check the typed answer against upstream `answer`: confidence is max probability, noul is probability of true, choice is stable ordered argmax, score is expected level. Require probability sums within **1e-12**.

## Runtime comparison

Before accepting a pair, require identical rendered prompt hashes, exact input token IDs (checked privately and published as SHA-256 of little-endian u32 IDs), and identical candidate token IDs. Context is 8192, no context shifting, one resident process, Metal, one active call. Uzu performs prefill and candidate readout without generation. llama.cpp performs the production one-token completion to obtain next-token log probabilities; its extra sampled token is disclosed and not treated as generation throughput.

Run two resident rounds with reversed engine load order; completely reap one engine before loading the next. Within each round, run all cases in the same fixed order. Each case gets a fresh call (`cache_prompt:false`) followed immediately by an identical-repeat call. llama.cpp permits only the consecutive exact token sequence to reuse state. Uzu initially creates fresh state for both calls and reports `cache_hit:false`. These timing populations are separate. Include load time, peak resident memory, tokenizer time, scoring-request time, total decision wall time, and available engine prefill/readout timing. Exclude load time from resident decision latency; report p50/p95 and paired speed ratios for wall time and scoring requests. Break timings and paired ratios into input-length buckets below 256, 256–1023, 1024–4095, and 4096 or more tokens; publish empty bucket counts without inventing measurements. No concurrent GPU workloads are authorized by this harness.

Predeclare engine probability labels: **strict match** if every paired option absolute difference is at most **1e-3**; **close match** if every difference is at most **1e-2**; otherwise **different**. These are descriptive engineering tolerances, not fitted calibration. Report mean/max absolute difference, L1, total variation, stable argmax agreement, and confidence/noul/expected-score differences. A screening target is at least **99% argmax agreement**, with maximum typed scalar differences **1e-3**; disclose every failure count rather than rounding into a pass. Near-tied choices may change with small differences.

## Quality and calibration

Report public-set argmax accuracy, rounded expected-value accuracy for score questions (Python round, matching JevBench), ordinal MAE, multiclass Brier sum against one-hot labels, and top-label ECE with 10 equal-width bins. ECE uses argmax correctness for all types; score rounded-EV correctness is reported separately. Report tier and question-type breakdowns. There are no exact gold distributions in these 231 source files, so do not invent a distribution-distance target.

Use the first fresh measurement per engine/case for quality; later measurements test numerical stability. Report paired differences and a 20,000-draw paired bootstrap 95% percentile interval, fixed seed 20261010. Screening margins are **1 percentage point accuracy reduction** and **0.01 Brier/ECE increase**. Passing a point-estimate margin alone does not establish noninferiority; uncertainty and the public development nature of the set must be stated. Do not refit temperature, inspect private research datasets, or infer universal calibration from this test.

## Privacy and reproduction

Raw public inputs, token IDs, logits, probabilities, decisions, and inference responses remain in owner-only files under ignored `test-artifacts/`. Console output contains authored status codes and counts only. Tracked provenance and reports contain source links, hashes, protocol/artifact identities, scalar metrics, and counts. No raw request, answer, option, key, or exception dump is logged. Private records are sealed by SHA-256 and aggregation verifies their input identities.

Run `uv run --locked python scripts/benchmark_jev_uzu.py prepare`, then `uv run --locked python scripts/benchmark_jev_uzu.py run --uzu-model MODEL_DIRECTORY --gguf GGUF_PATH --output test-artifacts/jev-uzu-screen`, then `uv run --locked python scripts/benchmark_jev_uzu.py aggregate --run test-artifacts/jev-uzu-screen --report REPORT_PATH`. The run command accepts explicit binary/reaper paths and two rounds by default. `--resume` resumes only matching sealed configuration and complete engine blocks; partial blocks fail closed and should use a fresh output directory.
